# 公告联系人字段（contact_name / contact_tel）数据质量问题解决文档

> 项目：基于 MCP 协议的联网搜索服务（招投标场景）— 数据采集模块
> 涉及数据：`ccgp_*_data_v2.csv`（9 个类别，共 4016 条）
> 涉及代码：`整合.py`（解析逻辑）、`修复联系人.py`（存量数据修复脚本）
> 日期：2026-09-11

---

## 一、问题现象

在数据验收阶段发现 `contact_name` / `contact_tel` 两个字段存在**人与电话错配、值粘连**的问题，典型样例：

| 公告 | 修复前的值 | 问题 |
|---|---|---|
| 公安部大数据中心2025式被装（第二批）采购项目询价公告 | 联系人 `联系代表电话`，电话 `010-662721112` | 名字混入"电话"二字；电话尾号多了 `2`，且配到的是采购人电话而非项目电话 |
| 拉萨海关行包辐射探测设备采购项目 | 电话 `010-65194838（` | 尾部残留未闭合括号 |
| 中国科学院昆明动物研究所项目 | 电话 `0871-65190773 2` | 电话后粘着段落编号 `2` |
| 中央国家机关政府采购中心系列公告 | 电话 `82961377-1252` | 分机号后粘着段落编号，分机被污染 |
| 部分公告 | 电话 `0574-88` | 电话号码在正文中跨 HTML 换行，只捕获到前半段 |

全库波及范围：累计修正约 **1900 / 4016 行**。

---

## 二、根因分析

ccgp 公告正文的"联系方式"部分是自由排版文本，问题由以下五个原因叠加造成：

### 2.1 正文空白压缩导致段落编号与电话粘连

页面原始 HTML 中，上一段落的联系电话与下一段落的编号之间没有可见分隔，文本流抽取并压缩空白后变成：

```
联系方式：010-66272111 2.采购代理机构信息名称：……
```

电话 `010-66272111` 与段号 `2.` 直接粘连。编号还可能是**全角句点**（`2．采购`），早期清洗规则未覆盖。

### 2.2 电话提取配到了"非项目"联系块

公告正文通常依次出现三块联系方式：**采购单位 → 采购代理机构 → 项目联系方式**。早期正则取全文第一个"联系方式："标签，配到的是**采购人**的电话，与 `contact_name`（取自"项目联系人："锚点）来源不一致，造成**人、电话错配**。

### 2.3 联系人名字吞并了后续标签词

"项目联系人：联系代表 电话：021-33292999"这类写法中，名字捕获只限制了汉字字符类，"电话"二字也是汉字，被一路吞进名字，得到 `联系代表电话`。

### 2.4 电话号码跨 HTML 换行被截断

正文里电话按 `0574-88\n3535613` 排版（HTML 换行），正则的字符类若不包含换行，只会捕获到 `0574-88`。

### 2.5 结构化表格提取在改造中丢失

ccgp 部分公告（尤其询价频道）的 `div.table` 中有**配对正确的** `项目联系人 / 项目联系电话` 表格字段，但改造后的解析函数只做正文正则、未用表格，放弃了页面上的权威数据源。

此外，`（010）8237 0045（传真…` 这类值在中文处截断后残留尾部 `（`，属于边界清理缺失。

## 三、解决方案

### 3.1 解析逻辑重构（`整合.py`，对后续增量采集生效）

`extract_contact_info` 改为**三级策略**：

```
① 结构化表格优先：div.table 中 项目联系人/项目联系电话 td，天然配对正确
② 正文锚点配对：先定位"项目联系人："，电话只在该位置之后查找，
   避免配到前面采购人/代理机构块
③ 正则回退前的预处理：移除换行（解决跨行截断），兼容
   "电话/联系电话/联系方式"及中间含空格的变体
```

### 3.2 电话清洗函数（`_clean_contact_tel`）

按序执行四步清洗：

1. **段内截断**：按 `数字? [.、．] 中文` 的边界截断捕获串内的编号粘连；
2. **串外段号剥除**：捕获串后紧跟 `.` 或 `．` 时，尾部 1~2 位孤立数字按号型校验决定是否剥除；
3. **空白移除**：删除所有内部空白（电话号码内部空白仅为排版）；
4. **尾部清理**：去掉未闭合括号与游离标点。

### 3.3 号型校验（核心防误伤机制）

剥除段号必须通过 `_should_strip_trailing` 的号型校验，按号码类型分别约束，**避免把合法号码的尾号当段号切掉**：

| 号码类型 | 判定 | 剥除条件（剥掉 k 位后） |
|---|---|---|
| 手机 | 主号 1 开头 | 主号恰好 11 位 |
| 固话 | 主号 0 开头（含区号） | 主号 10~12 位；无分隔符时要求原主号超长或带分机 |
| 本地号 | 无区号 | 主号 7~8 位；无分隔符时要求原主号超长或带分机 |

其中"主号"由 `_main_phone_digits` 计算——**分机号（`-` 或 `转` 之后的部分）不计入主号**，这样才能正确处理 `010-62555131-6395 2．` 这种"固话+分机+段号"的三重叠加场景：剥掉 `2`，保留 `010-62555131-6395`。

### 3.4 名字清洗（`_clean_contact_name`）

裁掉名字尾部粘连的标签词（`电话`/`联系方式`）：`联系代表电话` → `联系代表`。

## 四、存量数据修复（`修复联系人.py`）

由于 v2 数据已将**正文全文（content_text）入库**，修复无需重新请求网络：

1. 逐行读取 9 份 `*_data_v2.csv`；
2. 用新的 `extract_contact_info(None, content_text)` 从已存正文重新提取两个字段；
3. 仅在提取到新值时覆盖，否则保留原值（防止把好数据改空）；
4. 首次修改前备份原文件为 `*.csv.bak`（重复运行不覆盖最早备份）。

脚本可重复执行、幂等收敛，共迭代运行 5 轮，随清洗规则逐版完善，累计修正约 1900 行。

## 六、遗留说明与后续建议

1. **正文回退的天然局限**：询价频道部分公告的结构化表格里有真实人名（如"张雅嫚"），但正文"项目联系方式"节只写"联系代表"。本地修复基于已存正文，取到的是 `联系代表`（配对正确）。若需表格版人名，重爬 xjgg 单频道即可（约 20 分钟，解析逻辑已支持表格优先）。
2. **正常多联系人格式**：`010-63905975、孟雨` 这类"电话+第二联系人"的顿号结构是数据源本来的写法，判定规则已明确排除，不做切割。
3. **对后续环节的意义**：contact_tel 是商机探查场景的直连入口，本次修复后可直接作为 MCP 详情工具的可靠返回字段；`content_text` 入库 + 本地重提取的路径也验证了"正文一次采集、字段反复迭代"的架构收益。
4. **备份管理**：9 份 `*.csv.bak` 为修复前原始数据，验收确认后可删除。
